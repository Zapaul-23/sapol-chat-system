> เวอร์ชัน 0.2 · 26 ก.ย. 2026 · สถานะ: **Do เสร็จ → Check** (ผลอยู่ที่ `docs/CHECK-ACT.md`)
> ลำดับงาน: ทำ Support เป็นโปรแกรมแยกก่อน (โฟลเดอร์นี้) แล้วค่อยรวมกับ Sapol Chat ตาม `../docs/PLAN-R4.md` — ดูข้อ 10
> เงื่อนไข: ใช้ในการเรียน ไม่ซับซ้อน ทำเสร็จภายใน **2 ชั่วโมง** · เขียนโค้ดใน VS Code

## 1. เป้าหมาย

สร้างเว็บ **Customer Support แบบ Ticket + แชทสด** ให้ลูกค้าแจ้งปัญหาแล้วคุยกับเจ้าหน้าที่แบบเรียลไทม์ โดยทุก ticket และข้อความถูกเก็บลงฐานข้อมูล

**จบงานเมื่อ:** ลูกค้าเปิด ticket ได้ → เจ้าหน้าที่เห็น ticket ใหม่ทันที → ทั้งสองฝั่งแชทกันได้ → เจ้าหน้าที่ปิดงาน → ลูกค้าให้คะแนนได้

## 2. ผู้ใช้ (Actor)

| ผู้ใช้ | ทำอะไรได้ |
|---|---|
| **ลูกค้า** (ไม่ต้องล็อกอิน) | เปิด ticket, แชทใน ticket ของตัวเอง, ให้คะแนนเมื่อปิดงาน |
| **เจ้าหน้าที่** (ใส่รหัสผ่านร่วม) | ดูรายการ ticket ทั้งหมด, ตอบแชท, เปลี่ยนสถานะ |

## 3. ขอบเขต

| ทำ (5 ฟีเจอร์) | ไม่ทำ (รอบนี้) |
|---|---|
| **F1** ลูกค้ากรอกฟอร์มเปิด ticket (ชื่อ, อีเมล, หมวด, หัวข้อ, รายละเอียด) แล้วได้เลข ticket + ลิงก์ติดตาม | ระบบสมาชิก / ล็อกอินลูกค้า |
| **F2** แชทสดระหว่างลูกค้า ↔ เจ้าหน้าที่ภายใน ticket พร้อมประวัติข้อความ | ส่งอีเมล / แจ้งเตือนมือถือ |
| **F3** หน้าเจ้าหน้าที่: รายการ ticket กรองตามสถานะ อัปเดตทันทีเมื่อมี ticket หรือข้อความใหม่ | มอบหมายงานให้เจ้าหน้าที่หลายคน, SLA |
| **F4** เปลี่ยนสถานะ `ใหม่ → กำลังดำเนินการ → แก้ไขแล้ว` ลูกค้าเห็นทันที | แนบไฟล์ / รูปภาพ |
| **F5** เมื่อ "แก้ไขแล้ว" ลูกค้าให้คะแนนความพึงพอใจ 1–5 ดาว (CSAT) | Chatbot / ตอบอัตโนมัติ, dashboard กราฟ |

**ข้อกำหนดด้านความปลอดภัยขั้นต่ำ**

1. แสดงข้อความด้วย `textContent` เท่านั้น (ห้าม `innerHTML`) กัน XSS
2. ลูกค้าเข้าดู ticket ได้ด้วย **token สุ่ม** ที่ได้ตอนเปิด ticket เท่านั้น — เดาเลข ticket แล้วดูของคนอื่นไม่ได้
3. เจ้าหน้าที่ต้องใส่รหัส (`AGENT_KEY` ตั้งใน environment, ค่าเริ่มต้น `agent123` สำหรับเรียน)
4. ตรวจความยาวข้อมูล: หัวข้อ ≤ 100 ตัว, ข้อความ ≤ 1,000 ตัว, ตัดช่องว่างและข้อความว่างทิ้ง

## 4. เทคโนโลยี

| ส่วน | ใช้ | เหตุผล |
|---|---|---|
| Runtime | Node.js 22.5+ (เครื่องนี้ v22.23) | มี SQLite ในตัว (`node:sqlite`) ไม่ต้องติดตั้งเพิ่ม |
| Web server + API | Express | เหมือนโปรเจกต์แชทเดิม |
| Realtime | Socket.IO (ใช้ **rooms**) | ต่อยอดจาก Sapol Chat |
| ฐานข้อมูล | SQLite ไฟล์เดียว `data/support.db` | เบา ไม่ต้องตั้ง server |
| หน้าเว็บ | HTML + CSS + JS ธรรมดา 3 หน้า | ไม่ต้องใช้ framework |
| ทดสอบ | `node --test` + `socket.io-client` | test อัตโนมัติสั้น ๆ |

## 5. การออกแบบ (Design)

### 5.1 โครงสร้างระบบ

```
┌─ ลูกค้า ───────────────┐                    ┌─ server.js ────────────────────────┐
│ index.html  (เปิด ticket)│ ── REST (HTTP) ──▶ │ Express  /api/...                  │
│ ticket.html (แชท+ให้ดาว) │ ⇄  WebSocket  ⇄   │ Socket.IO                          │
└─────────────────────────┘                    │   room "ticket:<id>"  ← ลูกค้า+จนท. │
┌─ เจ้าหน้าที่ ───────────┐                    │   room "agents"       ← จนท.ทุกคน   │
│ agent.html (รายการ+แชท)  │ ⇄  WebSocket  ⇄   │ db.js ──▶ SQLite data/support.db   │
└─────────────────────────┘                    └────────────────────────────────────┘
```

- สร้าง/อ่าน ticket ผ่าน **REST** (ข้อมูลที่ทำครั้งเดียว)
- แชทและการแจ้งเปลี่ยนแปลงผ่าน **Socket.IO** (ข้อมูลที่ต้องเห็นทันที)
- ห้อง `ticket:<id>` ส่งหาแค่คนใน ticket นั้น, ห้อง `agents` ใช้แจ้งเจ้าหน้าที่ทุกคนว่ามี ticket/ข้อความใหม่

### 5.2 Flow หลัก

```
ลูกค้า                         Server                           เจ้าหน้าที่
  │ POST /api/tickets ─────────▶ บันทึก ticket (status=new)
  │ ◀── { id, code, token }      │── emit "ticket:new" ──────────▶ รายการเด้งขึ้น
  │ เปิด ticket.html?id&token    │
  │ join { id, token } ─────────▶ ตรวจ token → เข้าห้อง ticket:id
  │ message "เข้าเว็บไม่ได้" ───▶ บันทึก → emit ห้อง + "agents" ──▶ badge ยังไม่อ่าน
  │                              │ ◀─────────── join (agentKey) + message "ลองล้างแคช"
  │ ◀── message                  │
  │                              │ ◀─────────── status "resolved"
  │ ◀── status → แสดงดาว 1–5      │
  │ rate 5 ─────────────────────▶ บันทึกคะแนน ──── emit "ticket:updated" ──▶
```

### 5.3 สถานะ ticket

```
 ┌──────┐  จนท.ตอบครั้งแรก/กดรับงาน  ┌──────────────┐   จนท.กด   ┌───────────┐
 │ new  │ ─────────────────────────▶ │ in_progress  │ ─────────▶ │ resolved  │
 │ ใหม่ │                            │ กำลังดำเนินการ │ ◀───────── │ แก้ไขแล้ว  │
 └──────┘                            └──────────────┘ ลูกค้าพิมพ์  └───────────┘
                                                      ต่อ (เปิดใหม่)
```

- จนท. ส่งข้อความแรกใน ticket `new` → เปลี่ยนเป็น `in_progress` อัตโนมัติ
- ลูกค้าส่งข้อความใน ticket `resolved` → กลับเป็น `in_progress` (และล้างคะแนนเดิม)
- ทุกครั้งที่เปลี่ยนสถานะ ระบบใส่ข้อความ system ในแชท เช่น "— สถานะ: แก้ไขแล้ว —"

### 5.4 ฐานข้อมูล

**ตาราง `tickets`**

| คอลัมน์ | ชนิด | หมายเหตุ |
|---|---|---|
| id | INTEGER PK | auto |
| code | TEXT | แสดงผล เช่น `CS-0001` |
| token | TEXT | สุ่ม 32 ตัว (`crypto.randomBytes`) ใช้แทนการล็อกอินลูกค้า |
| customer_name | TEXT | ≤ 50 |
| email | TEXT | ตรวจรูปแบบเบื้องต้น |
| category | TEXT | `general` สอบถาม / `technical` ปัญหาการใช้งาน / `billing` การชำระเงิน |
| subject | TEXT | ≤ 100 |
| status | TEXT | `new` / `in_progress` / `resolved` |
| rating | INTEGER NULL | 1–5 |
| created_at, updated_at | TEXT | ISO time |

**ตาราง `messages`**

| คอลัมน์ | ชนิด | หมายเหตุ |
|---|---|---|
| id | INTEGER PK | |
| ticket_id | INTEGER FK | → tickets.id |
| sender | TEXT | `customer` / `agent` / `system` |
| sender_name | TEXT | |
| text | TEXT | ≤ 1,000 (รายละเอียดตอนเปิด ticket = ข้อความแรก) |
| created_at | TEXT | |

### 5.5 REST API

| Method | Path | ใครเรียก | ส่ง / ได้ |
|---|---|---|---|
| POST | `/api/tickets` | ลูกค้า | ส่ง `{name, email, category, subject, detail}` → ได้ `{id, code, token}` |
| GET | `/api/tickets/:id?token=` | ลูกค้า | ได้ ticket + ข้อความทั้งหมด (token ผิด → 404) |
| GET | `/api/agent/tickets?status=` | จนท. (header `x-agent-key`) | รายการ ticket + ข้อความล่าสุด + จำนวนยังไม่อ่าน |
| GET | `/api/agent/tickets/:id` | จนท. | ticket + ข้อความทั้งหมด |

### 5.6 Socket.IO Events

| ทิศทาง | Event | ข้อมูล | ความหมาย |
|---|---|---|---|
| ลูกค้า → server | `join` | `{ticketId, token}` | เข้าห้อง ticket |
| จนท. → server | `agent:login` | `{agentKey, name}` | เข้าห้อง `agents` |
| จนท. → server | `join` | `{ticketId}` | เปิดดู ticket (ต้อง login แล้ว) |
| ทั้งคู่ → server | `message` | `{ticketId, text}` | ส่งข้อความ |
| จนท. → server | `status` | `{ticketId, status}` | เปลี่ยนสถานะ |
| ลูกค้า → server | `rate` | `{ticketId, rating}` | ให้คะแนน (เฉพาะ resolved) |
| server → ห้อง ticket | `message` | `{sender, sender_name, text, created_at}` | ข้อความใหม่ |
| server → ห้อง ticket | `status` | `{status}` | สถานะเปลี่ยน |
| server → `agents` | `ticket:new` / `ticket:updated` | ข้อมูลย่อของ ticket | ให้รายการฝั่ง จนท. อัปเดต |
| server → ผู้ส่ง | `error_msg` | `text` | แจ้งข้อผิดพลาด (token ผิด, ข้อความยาวเกิน ฯลฯ) |

## 6. แผนการทำงาน (ขั้น Do) — รวม 120 นาที

| นาทีที่ | งาน | ตรวจได้ว่าเสร็จเมื่อ |

| 100–120 | เขียน test + ทดสอบด้วยมือตามข้อ 7 | ผ่านครบ 10 ข้อ |

## 8. ความเสี่ยง

| ความเสี่ยง | แนวทาง |
|---|---|
| `node:sqlite` ขึ้นคำเตือน ExperimentalWarning | ปกติ ใช้งานได้ (ถ้ารำคาญ รันด้วย `node --no-warnings server.js`) |
| Node ต่ำกว่า 22.5 | อัปเดต Node LTS หรือเปลี่ยนเป็นเก็บไฟล์ JSON |
| PowerShell บล็อก `npm` | เปลี่ยน Terminal ใน VS Code เป็น Command Prompt |
| พอร์ตชนกับ Sapol Chat (3000) | Support ใช้พอร์ต **3100** |
| ลูกค้าทำลิงก์ ticket หาย | แสดงลิงก์เด่น ๆ พร้อมปุ่ม "คัดลอกลิงก์" (รอบถัดไป: ส่งลิงก์ทางอีเมล) |
| เวลาไม่พอ | ตัด F5 (ให้คะแนน) ออกก่อน แล้วย้ายไปรอบ Act |

## 9. ขั้น Act (รอบถัดไป เรียงจากง่ายไปยาก)

ปุ่มคัดลอกลิงก์ → "กำลังพิมพ์…" → ค้นหา ticket → ระดับความสำคัญ (priority) → มอบหมายงานให้ จนท. แต่ละคน → dashboard สถิติ (จำนวน ticket, เวลาตอบเฉลี่ย, CSAT เฉลี่ย) → ล็อกอินจริงด้วยรหัสผ่านเข้ารหัส → แจ้งเตือนทางอีเมล

## 10. เตรียมรวมกับ Sapol Chat (ออกแบบไว้ตั้งแต่รอบนี้)

| สิ่งที่ทำไว้ในโค้ดรอบนี้ | ทำไมช่วยตอนรวม |
|---|---|
| โครงไฟล์ `src/` + `server.js` จุดเริ่ม เหมือน Sapol Chat | ย้ายไฟล์เข้าโปรเจกต์แชทได้ตรง ๆ |
| กฎธุรกิจทั้งหมดอยู่ใน `src/tickets.js` ซึ่ง **ไม่รู้จัก Socket.IO / Express** | ย้ายไปเป็น `src/support.js` แล้วต่อสายใหม่ใน Gateway ของแชทได้ |
| ตารางชื่อ `tickets`, `ticket_messages` | ไม่ชนกับตาราง `messages` ของแชท |
| ตาราง `events` โครงสร้างเดียวกับแชท + event `TicketOpened / TicketStatusChanged / TicketRated` | ต่อ dashboard (Q7–Q10) ได้ทันที |
| ข้อความมี `sender` = `customer / agent / system` | ตรงกับแนวคิด `content_type = 'system'` ในแผนรอบ 4 |

**ขั้นตอนรวม (รอบถัดไป)**: ลูกค้า/เจ้าหน้าที่ใช้ username ของแชทแทน token และรหัสร่วม → ticket ผูกกับ conversation ชนิด `support` → `ticket_messages` ย้ายไปใช้ `messages` ของแชท (ได้ ✓✓ และคิว offline ฟรี) → หน้า `agent.html` ใช้ต่อได้เกือบทั้งหน้า
